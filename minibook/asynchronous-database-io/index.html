Asynchronous Database I/O

Submission, completion, concurrency, and durability boundaries

Reason about asynchronous database I/O from kernel submission queues through completion handling, backpressure, cancellation, and commit durability.

01

Asynchronous means work can overlap

An asynchronous interface separates submitting an operation from observing its completion. Its benefit comes from useful concurrency and reduced waiting or syscall overhead, not from making the storage device intrinsically faster.

  • Count operations in flight.
  • Measure queueing and completion latency separately.
  • Compare equivalent concurrency and cache states.

02

The kernel interface shapes overhead

io_uring uses shared submission and completion rings so PostgreSQL can issue reads and collect completions with fewer transitions. Capability, kernel version, and database release remain part of the result.

  • Confirm the selected I/O method at runtime.
  • Retain fallback behavior in tests.
  • Measure CPU time as well as elapsed time.

03

Prefetch and asynchronous I/O differ

Prefetch advises or initiates future reads while the current work continues; true asynchronous execution also exposes completion. Both need predictable access far enough ahead to hide latency.

  • Record requested, issued, and useful reads.
  • Sequential and bitmap access offer different look-ahead.
  • Over-prefetch can evict useful cache pages.

04

Backpressure protects the system

Unlimited outstanding I/O moves waiting into device queues and can inflate tail latency. A database needs bounded depth, fair scheduling, memory ownership, and cancellation when a query stops.

  • Sweep queue depth instead of maximizing it.
  • Observe p95 and p99 completion time.
  • Test cancellation and error cleanup.

05

Completion is not durability

A completed write may have reached a kernel or device cache without crossing the durability boundary. Commit safety still depends on write ordering, flush semantics, WAL, and the configured acknowledgement policy.

  • Distinguish write completion from stable-media acknowledgement.
  • Do not weaken durability to demonstrate throughput.
  • Test restart and power-failure assumptions.

06

Workload shape decides the gain

Random misses, sequential scans, cached reads, and writeback have different opportunities for overlap. Report block size, concurrency, hit ratio, storage topology, and CPU saturation with any benchmark.

  • Keep throughput and latency together.
  • Compare synchronous and asynchronous paths on identical data.
  • Reject improvements caused only by warmer cache.

07

Field manual

Concrete mechanics, diagnostic evidence, and executable patterns to carry into a real system.

01

Measure useful concurrency

Sweep outstanding operations while holding data, block size, and cache state constant. The useful depth is where throughput gains flatten before tail latency grows sharply.

for depth in 1 2 4 8 16 32:
  record throughput, p50, p95, p99, CPU, queue latency
# Repeat cold and warm; do not merge the populations.
02

Confirm PostgreSQL's I/O method

A benchmark must retain the PostgreSQL release, kernel, selected I/O method, and fallback messages so an io_uring result is reproducible.

SHOW io_method;
SELECT version();
-- Retain server startup log and kernel version with results.
03

Separate issue and completion

Instrumentation should timestamp queue admission, submission, device completion, and consumer wake-up. One aggregate duration cannot reveal backpressure.

queue_delay = submitted_at - admitted_at
service_time = completed_at - submitted_at
resume_delay = consumed_at - completed_at
04

Test cancellation and durability

Cancel work with I/O in flight, then verify buffers and resources are released. For writes, separately crash-test the configured commit boundary.

1. Start a bounded read with observable I/O in flight.
2. Cancel the statement and verify cleanup.
3. For write tests, acknowledge a commit, terminate the instance,
4. Restart and verify committed and uncommitted invariants.
